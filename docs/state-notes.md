# 状态管理

第三阶段加入 `modules/state/`，由 `TerminalRuntime` 在协议解析后更新。模块使用 Qt Core、身份定义和协议层，不依赖 MQTT 客户端或图形窗口。所有查询、更新和通知在所属 Qt 线程执行。

## 入口与分组

- `TerminalRuntime::stateStore()`：只读访问，调用 `topic()`、`robotTopic()`、`robotHealth()`、`buff()` 或 `snapshot()`。
- `TerminalRuntime::stateChanged(topic)`：消息更新时传 Topic；会话、连接或定时过期变化时 Topic 为空，调用方重新查询需要的状态。
- `TerminalRuntime::snapshot().business_state`：CLI 可查看的完整 JSON 快照。

状态快照包含以下分组，均引用同一份观测数据，不以角色过滤接收：

| 分组 | 含义 |
| --- | --- |
| `global` | 比赛、基地/前哨站、后勤、特殊机制、能量机关、哨兵和飞镖状态 |
| `self` | 配置绑定的机器人；指挥手为 `null` |
| `robots` | 已有观测的机器人，按绝对编号保存血量、各 Topic 和 Buff |
| `role` | 重装装配、步兵性能体系、指挥手哨兵/飞镖相关状态入口 |
| `topics` | 全部 23 个入站 Topic 的最新样本；未解析的雷达消息保持未知 |
| `recent_notifications` | 最近 128 条事件、判罚、地图点击、路径规划和哨兵指令结果通知 |

自定义数据流只保存最新载荷，不在内存中积累 50 Hz 历史；完整原始接收记录仍在 MQTT JSONL 文件中。通知窗口按收到的消息保存，MQTT QoS 1 可能重复投递，没有业务唯一编号时不猜测去重。

## 数据存在性

`StateValue` 将 `fields`、来源、年龄、超时和有效性一起返回。保留官方字段名，避免再维护一套重复命名；`uint64` 沿用 Protobuf JSON 的字符串形式，字节字段是 Base64。

标量只有本帧显式出现时才保存，包括显式的 `0` 和 `false`。更新同一 Topic 时整体替换本帧，不推断增量合并；上帧存在、本帧未发送的字段重新变为缺失。`repeated` 无字段存在性，空数组按空列表保存，可以清除旧列表。无法解析、超长、方向错误、schema 未确定、时间倒序或会话开始前的消息不覆盖状态。

这意味着 `isFresh()` 只说明样本的新鲜程度，不保证业务需要的每个字段都有值。C++ 读取示例：

```cpp
const auto health = runtime.stateStore().robotHealth(3);
if (health.isFresh() && health.fields.contains("current_health")) {
    const auto hp = health.fields.value("current_health").toInteger();
    // 这里的 0 是服务器明确发来的血量，不是缺失值的默认值。
}
```

当前没有推算血量、倒计时、比赛阶段或机器人动作，也没有实现指令结果与请求的关联。`SentryCtrlResult` 保存为结果通知，不能据此推断机器人动作已经完成。

## 有效性与时间

| `validity` | 含义 |
| --- | --- |
| `unknown` | 尚未收到数据，或收到的消息没有已知字段 |
| `fresh` | 周期状态在工程超时内，或 Buff 的服务器剩余时间尚未到期 |
| `stale` | 超时，或重连后仍属于上一连接的样本 |
| `disconnected` | 连接中断或后端停止，值只供查看历史 |
| `retained` | Broker 保留消息；协议无源端时间，不能证明它是当前状态 |
| `observed` | 条件/事件类消息，表示收到过，不承诺其效果持续生效 |

每个已接收样本保存来源 Topic、会话、连接代次、UTC 接收时间、单调接收时间、retained 标记和机器人归属。UTC 用于对照日志，新鲜度只使用 `steady_clock`，避免系统校时影响。

周期消息超时暂设为 `max(500 ms, 三个发送周期)`：比赛状态为 600 ms、机器人动态为 500 ms、1 Hz 状态为 3000 ms、自定义数据流为 500 ms。这是工程策略，不是官方保证，尚未增加个人配置项。Buff 按各自 `buff_left_time` 秒独立到期，零秒立即标记过期，不生成虚构的“增益为零”消息；未给出剩余时间时只标记 `observed`。

事件和条件通知没有固定发送周期，不套用周期超时。有效性每次查询实时计算；连接期间内部定时器每 100 ms 检查状态转变，因此没有新消息时也会发出过期通知。

断线保留数据并立即失效；重新连上后旧样本保持 `stale/previous_connection`，收到对应新消息才能恢复。订阅请求期间即可接收入站状态，全部订阅是否成功仍以 MQTT 的 `ready` 为准，样本新鲜不代表全部 Topic 已获授权。每次启动新会话清空状态、Buff 和通知窗口；同一会话内不猜测官方局次切换时未发送的字段。

## 机器人归属与血量

- 明确带机器人编号的消息按该编号归属，不覆盖其他机器人。
- 缺少编号的机器人私有状态按本地配置绑定；这不是服务器身份认证。指挥手没有绑定编号，消息仍保存在 `topics`，不猜测它属于某台地面机器人。
- Buff 同时按机器人编号与类型保存，避免不同增益互相覆盖；缺少编号或类型时只保存最新 Topic 样本，不猜测归属。机器人索引限于 1/3/4/7/101/103/104/107，Buff 索引限于协议定义的 1–7，未知值仍可在 Topic 中检查。
- 全局血量数组按官方顺序“己方 1/3/4/7，对方 1/3/4/7”结合阵营转换为绝对编号；仅完整八项时建立映射，缺失或长度异常会清除这一路旧映射。
- `robotHealth()` 优先返回新鲜的机器人动态血量，其次是新鲜的全局血量；都不新鲜时返回最近一次有值的观测并保留无效标记。不会把全局血量写回私有 Topic，也不把血量 0 推断为机器人具体存活枚举。

## 验证范围

状态单元测试通过可控单调时钟验证超时边界、字段缺失、显式零值、数组清空、不同 Buff、蓝方映射、来源选择、断线重连、会话重置和通知窗口；内部定时器也有实际事件循环验证。MQTT 集成测试验证真实本地 Broker 到运行层状态查询的链路、坏包隔离、停止失效、重连等待新样本和重新启动清空。

官方引擎的实际身份、字段发送条件、权限、标量是否增量发送和真实网络波动尚待现场确认；当前保持缺失字段，不凭本地测试宣称实机数据已经完整。
