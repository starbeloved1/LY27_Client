## 已确定的方向

- 与官方选手端配合使用，优先承担额外的作业、赛事交互和战术辅助任务，首版不以完整替代官方选手端为目标。
- 首页以提供比赛信息为主，参考 RM26 的总览信息层级：比赛与设施状态、双方机器人状态、战场地图、经济和关键事件；具体布局与风格独立设计，不照搬 26 赛季角色、数值和规则。
- 重装与指挥手共享信息总览基础。重装增加装配及自身专项状态，指挥手增加所需的队伍/战术信息和可用交互；角色专项内容作为局部模块或独立面板，不占据整个首页。
- 首页不做大型机器人模型展示、机械结构教学、装配操作向导或大按钮操作台。此前以装配模型为中心的概念图已被用户否定，不作为后续设计基线。伪三维仅作为表现手段，不改变信息优先级。
- 主界面默认不使用图传，不预留强制视频中心区，不以收到视频作为页面可用条件。此前以全屏图传为中心的概念图不作为本方案的布局依据。
- 保留已经实现的视频后端与 CLI 功能，未来确有需要时再增加独立图传入口。默认不启动接收和解码，不在隐藏页面持续拉流。
- 步兵暂不作为首批前端页面，保留现有后端角色、协议和业务能力。未来扩展时复用同一套后端和公共界面组件。
- 控制输入、自定义控制器、记录回放和地图标记以外的终端协同仍按原安排暂缓。首版按钮和面板交互不等于已接入连续键鼠操控上传。

旧代码中的页面直接调用 `NetworkManager`、主窗口同时持有大量业务逻辑、无数据时使用模拟值等路径不作为迁移方案。不直接复制整个页面或旧赛季业务条件；本次兼容适配仅按用户授权修改 RM26 模拟器，默认 2026 模式保持原行为。

## 前端与后端的连接

```text
apps/desktop/src/main.cpp
  ├─ 创建日志与 TerminalRuntime，统一启动和停止
  └─ 创建前端展示适配与主窗口
       ├─ 主窗口：角色页面、导航、弹层
       ├─ 重装工作台：比赛信息总览、专项状态及独立业务面板
       └─ 指挥手工作台：队伍状态、地图、事件及相关业务面板

StateStore ──查询与刷新──> C++ 展示适配 ──界面数据──> 页面与组件
页面与组件 ──操作意图──> C++ 展示适配 ──类型化请求──> CommandDispatcher
TerminalRuntime ──配置、连接、提交记录等通知──> C++ 展示适配
```

前端展示适配是 UI 模块内的小型 C++ 层，承担以下职责：

- 从 `runtime.stateStore()` 的类型化结构读取数据，转换为可绑定的字段、列表、文本和可操作状态，不解析原始 MQTT 数据或依赖诊断 JSON 拼业务。
- 监听 `stateChanged`、`configurationChanged` 和 `commandObserved` 等通知；按需要定时重新查询时效性，使没有新消息时的过期状态与倒计时也能刷新。
- 保留缺失、过期、断线和未知的区别；不以零或演示数据替代缺失状态，不在 UI 内复制协议存储和赛事规则。
- 将按钮操作转换为已有类型化请求，通过 `runtime.commands()` 提交；保留后端最终参数、角色、状态和频率检查，不在界面中直接发布 MQTT。
- 对接配置应用、身份切换和错误反馈。身份仍来自当前运行配置，不因切换标签页而偷偷改变服务器通信身份。
- 将已提交、传输确认、执行结果未知和实际赛事反馈分开展示，不凭发送成功显示业务完成。

首版优先用一个展示适配入口；只有在实际文件职责变多后，才拆出装配、队伍列表或地图的专用展示模型，不提前为每个 Topic 创建管理器或服务。

## 代码位置

当前已创建桌面入口和单窗口 UI 模块；后续文件按实际功能增加，不提前创建空类。完整模块增长后的组织目标为：

```text
apps/desktop/
├── CMakeLists.txt
└── src/main.cpp             桌面入口与应用对象生命周期

modules/ui/
├── CMakeLists.txt
├── include/                 展示适配、主窗口、角色工作台与业务面板的 .hpp
└── src/                     对应的 C++ 实现
```

仍遵循模块内 `include/`、`src/` 和 `.hpp` 约定；只有一个手写头文件与一个实现文件的模块使用已有简化规则。视图资源按选定的 Qt 技术及实际组件需求组织，不恢复旧项目一整个 `src/` 共用所有后端文件的布局。

`modules/ui/` 使用应用、状态和指令的公开接口；现有后端模块不依赖 UI。`apps/cli/` 继续独立运行，桌面依赖只在接入桌面构建目标时添加，不让无界面 CLI 因桌面环境缺失而无法构建或启动。

先完成单窗口、一个当前角色工作台。多屏扩展后续再按实际需求设计；多个显示窗口应共用同一个后端，不能因增加屏幕而重复连接 MQTT、重复订阅或独立发送同一操作。

## 具体接入顺序

1. **最小桌面入口。** 增加桌面构建目标，复用日志、配置和 `TerminalRuntime`；创建主窗口及当前角色的最小工作台，默认关闭图传。先验证启动、停止、断线和身份切换，保留 CLI。
2. **基础展示与操作反馈。** 接入比赛、连接、身份、资源等已有状态，统一设置、错误提示、确认和提交记录。首批数据来自现有后端，不为填满页面补模拟值。
3. **重装业务。** 接入装配状态与开始、步骤确认、退出等已有指令，以及需要的兑换、性能选择等面板。实际服务器开放条件继续由后端与赛事环境验证，不照搬 26 数值和提示。
4. **指挥手业务。** 接入队伍与设施状态、事件列表，再完成地图显示、坐标转换和可用交互；按已核实的角色权限接入相应操作。地图渲染、提醒策略和分析功能是后续实现内容，不因接收了协议就视为已完成。
5. **整理页面交互与视觉。** 在功能路径可用后统一布局、风格、键帽提示和动效。快捷键沿用已核对的操作习惯并处理角色、焦点和弹窗冲突，具体参考 `input-reference.md`；控制设备采集和连续上传仍需单独接入。

当前已实现桌面入口、窗口、图片底图、比赛/设施展示适配、机器人状态叠加和地图坐标转换；地图标记选项弹层已接入，详见 `tactical-map.md`；角色专项页面、设施独立详情及其他弹层仍待接入。接下来按用户确定的信息需求逐项推进，不自动实现上面的全部步骤。
