# 图传接入说明

## 接收范围

接入 2027 通信协议 V1.0.0 第 46 页的官方图传接口：UDP 3334，HEVC/H.265，文档标称 1920×1080、60 fps，无重传。该接口平时即可使用，不依赖 MQTT，也不是飞镖致盲后才开放。规则 V1.0.0 第 111 页明确自定义终端在界面被遮挡时仍可接收图传数据。

不解析 MQTT 自定义字节中的自制视频，不增加其他摄像头链路。自定义数据内容仍保留接口。

## 模块与使用

`modules/video/` 内包含：

- `VideoTypes.hpp`：编码帧、解码图像与时间来源。
- `VideoAssembler.hpp/.cpp`：包头校验、分片重组、超时清理与帧号处理。
- `HevcDecoder.hpp/.cpp`：FFmpeg 软件解码、RGB 图像转换及关键帧恢复。
- `VideoReceiver.hpp/.cpp`：UDP、工作线程、有限队列、最新帧与状态通知。

后端调用 `runtime.start(enableMqtt, enableVideo)`。默认均关闭，启用图传不要求启用 MQTT。视频由 `TerminalRuntime` 启停，启动失败回收已启动的通信资源；重启清除上一会话的图像和统计。

```cpp
runtime.start(false, true);
QObject::connect(&runtime, &ly27::TerminalRuntime::videoFrameAvailable, consumer, [&runtime] {
    const auto frame = runtime.video().latestFrame();
    if (!frame) return;
    // 使用 frame->image；它拥有自己的内存，可保留到下一次更新。
});
```

应在后端所属线程查询接口。`videoStateChanged` 通知 `waiting`、`streaming`、`stale`、`stopped` 或 `error`；未启用为 `disabled`。`waiting` 只表示已绑定 UDP 端口，不表示已经收到可用图像。超过首个分片接收时间 500 ms 的图像不再由 `latestFrame()` 返回，消费者应根据状态更新移除旧画面或明确标记失效。时间取本机接收时刻，不能当作相机采集时间或端到端延迟。

状态快照的 `video` 包含实际端口、组帧/解码数量、无效包、过期帧、重复或旧包、队列溢出、解码错误、等待关键帧与图像新鲜度等。`modules.video` 是该模块当前状态。

## 网络配置与 CLI

继续使用 `network.video_port`。新增两个可选字段，旧配置省略时兼容：

```json
"video_port": 3334,
"video_bind_address": "127.0.0.1",
"video_source_address": ""
```

默认只监听回环地址，适合本机模拟。现场应把 `video_bind_address` 改为本机赛事网卡 IPv4 地址，或显式设置 `0.0.0.0`；按协议设置现场 IP。`video_source_address` 可指定发送端 IPv4；这是视频来源，不根据 MQTT Broker 地址推断。留空时锁定首个合法分片的来源 IP 和源端口，防止两路发送者拼在一起；停流一秒后允许重新锁定。来源过滤不提供身份认证。

```bash
# 单独启用图传，退出时打印统计。
./build/local-dev/bin/ly27_cli --video --run-for 5000 --status-at-exit

# 无图形窗口，把第一张新鲜图像保存为 PNG；目录需要已经存在。
./build/local-dev/bin/ly27_cli --video --run-for 5000 --save-frame /tmp/ly27-frame.png --status-at-exit

# 同时启用状态、指令通信和图传。
./build/local-dev/bin/ly27_cli --mqtt --video
```

`--save-frame` 需要 `--video` 和 `--run-for`。只写第一张新鲜帧，采用原子文件替换；到时未收到画面或写文件失败返回退出码 `6`，失败时不产生假图像。端口绑定或解码器初始化失败沿用退出码 `4`。未指定 `--save-frame` 时，没有画面仍可正常运行，通过快照判断状态。

Qt Gui 仅用于 `QImage`，继续使用 `QCoreApplication`，不需要显示服务器、Widgets 或 QML。

## 包格式与工程策略

每个 UDP 数据报最多 1400 字节，前 8 字节均为大端：`uint16 帧号 + uint16 分片序号 + uint32 当前帧总字节数`；剩余至多 1392 字节是码流。

- 按分片序号拼接，去重，要求序号连续且总字节数严格相等。缺失、冲突、溢出或长度不符的帧不送入解码器。
- 官方未说明分片序号从 0 还是 1 起，当前兼容这两种连续序号；不强制每个非末分片填满 1392 字节。
- 接受帧号的 16 位回绕，已经输出的旧帧不再次送入解码；新帧先完成时丢弃后来完成的旧帧。乱序导致跳帧时优先保守恢复，避免倒序解码。
- 重组期限 150 ms；单帧最多 4 MiB、4096 片，最多缓存 8 个未完成帧，总分片数据不超过 16 MiB。这些是工程保护值，不是官方协议新增限制。
- 解码队列最多 4 帧；满时丢弃积压，按不连续码流恢复。工作线程每轮最多读取 256 个数据报，避免接收洪峰持续占用事件循环。
- 接收、组帧、解码均在独立工作线程。主线程每 16 ms 合并通知一次，线程间只保存最新图像，主线程卡顿不会产生无限图像队列。通知频率约 60 Hz，慢消费者直接读取最新帧。
- 帧号缺口、解码错误或停流一秒后刷新参考图像状态，等待 HEVC IRAP 关键帧；不重传，不显示缺片帧。停流恢复时允许发送端重新从小帧号开始。
- 当前按一个协议帧对应一个 Annex-B HEVC 访问单元送入解码器。官方未明确起始码、关键帧周期和 B 帧配置，需要真实码流进一步核实。FFmpeg 负责帧重排，保留每个输出帧的接收来源；不在停止时排空延迟帧来冒充实时画面。
- 图像上限为 4096×2160；当前采用 FFmpeg 软件解码、RGB888 输出，尚未接入硬件解码或零拷贝渲染。

## 已验证与待验证

本地 C++ 测试覆盖包头字节序、乱序与重复、冲突和缺片、超时与缓存上限、帧号回绕与停流重置、真实 HEVC 测试码流解码、丢帧后等待关键帧、UDP 来源隔离、过期、端口冲突、停止/重启与会话隔离、CLI 在无显示服务器环境导出 PNG，以及无画面导出失败。

测试素材由 FFmpeg 的测试图生成，不来自比赛录像；测试只用回环网络，不要求安装编码器。素材生成方式见 `tests/fixtures/README.md`。

尚未用真实赛事图传硬件验证：实际分片序号起点、码流访问单元边界、断流后发送端行为、关键帧及参数集策略、1080p60 持续性能与丢包恢复观感。当前测试通过不代表这些现场条件已验证。视频同步记录与回放仍属于第七阶段，本阶段不逐包写入运行日志或 MQTT JSONL。
